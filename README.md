# text2sql-guardrails

Агент, переводящий вопрос на естественном языке в SQL к PostgreSQL. Отличие от типового
NL→SQL — слой безопасности: языковая модель может ошибиться или сгенерировать разрушительный
запрос, поэтому перед выполнением каждый SQL проходит проверку, которая пропускает только
чтение. Демо-база — Northwind.

Главный вопрос проекта — не «насколько точно модель пишет SQL», а «как не дать ей уронить
базу». Пускать LLM с произвольным SQL к боевой БД нельзя, и ниже показано, чем именно
это ограничивается.

## Защита

Защита двухслойная. На уровне приложения каждый запрос разбирается и пропускается только
чтение. На уровне БД приложение ходит под ролью `text2sql_ro`, у которой есть право только
на `SELECT` — поэтому даже если разбор кто-то обойдёт, база физически не даст изменить
данные. Слои независимы и дополняют друг друга.

### Разбор запроса

Перед выполнением SQL разбирается через `sqlparse` на токены — не поиском слов по тексту,
а по типам выражений. Блокируется:

- всё, кроме одиночного `SELECT` или `WITH ... SELECT`;
- любой оператор записи или структуры на любом уровне вложенности — `INSERT`, `UPDATE`,
  `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `GRANT`, `CALL`, `COPY` и другие, в том числе
  внутри CTE вида `WITH x AS (DELETE ... RETURNING *) SELECT * FROM x`, который PostgreSQL
  выполняет, а по типу выражения он выглядит как `SELECT`;
- несколько выражений через `;` — защита от `SELECT 1; DROP TABLE ...`;
- опасные функции, доступные из обычного `SELECT`: чтение и запись файлов на сервере
  (`pg_read_file`, `lo_export`), выполнение команд (`COPY ... TO PROGRAM`), удержание
  соединения (`pg_sleep`), обрыв чужих сессий (`pg_terminate_backend`).

Ко всему, что прошло, принудительно добавляется `LIMIT`, а на соединение ставится
`statement_timeout` — тяжёлый запрос вроде декартова произведения не удержит базу.

Разбор по токенам, а не по словам, важен в обе стороны: слово `delete` внутри строкового
литерала или колонка `update_date` запрос не блокируют, а функция чтения файла внутри
безобидного с виду `SELECT` — блокирует.

### Роль только для чтения

`docker/init/zz_readonly_role.sql` создаёт роль `text2sql_ro` с единственным правом `SELECT`,
и приложение в `.env.example` настроено ходить под ней. Разбор запроса гибкий, но в нём
возможна ошибка; права БД грубые, но абсолютные — вместе они закрывают друг друга.

### Замер

Набор из 44 запросов: 26 попыток обхода и 18 легитимных
([tests/test_guardrails.py](tests/test_guardrails.py)). Обе реализации прогоняются по
одному набору — регулярный baseline лежит в
[tests/baseline_regex.py](tests/baseline_regex.py), а таблица воспроизводится тестом
[tests/test_comparison.py](tests/test_comparison.py):

| реализация | заблокировано атак | пропущено легитимных |
|---|---|---|
| поиск слов регуляркой | 20 / 26 | 14 / 18 |
| разбор по токенам | **26 / 26** | **18 / 18** |

```bash
pytest tests/test_comparison.py -s
```

Что пропускала версия на регулярке: чтение и запись файлов на сервере, `pg_sleep`,
`pg_terminate_backend`, `EXECUTE` после точки с запятой. Что блокировала зря: запросы,
где `delete` или `drop` встречались внутри строк и комментариев.

## Пайплайн

```
вопрос (RU)
   │  опционально переводится на EN — многим моделям так проще
   ▼
интроспекция схемы из Postgres (таблицы, колонки, внешние ключи)
   │
   ▼
поиск релевантных таблиц ──► few-shot промпт ──► Ollama ──► SQL
   │
   ▼
guardrails: только SELECT, блокировка DDL/DML/функций, принудительный LIMIT
   │
   ▼
выполнение ──► ошибка БД? ──► self-healing: повтор с текстом ошибки
   │                          + детерминированные фиксы частых галлюцинаций колонок
   ▼
таблица результата
```

Self-healing разбирает текст ошибки PostgreSQL (`UndefinedColumn`, `GroupingError`,
`operator does not exist`) и до `max_retries` раз переспрашивает модель, добавляя ошибку
в промпт. Плюс детерминированные замены известных галлюцинаций схемы Northwind
(`customer_name` → `company_name`).

Схема читается из `information_schema`, поэтому пайплайн не привязан к конкретной базе.
Проверено на трёх разных доменах без единой правки кода — менялась только переменная `PG_DB`:

| база | таблиц | домен |
|---|---|---|
| Northwind | 14 | торговля |
| Chinook | 11 | музыкальный магазин |
| Pagila | 11 | прокат фильмов |

На всех трёх интроспекция собирает схему, а агент генерирует и выполняет SQL.

## Быстрый старт

Нужны PostgreSQL с базой Northwind и локальная [Ollama](https://ollama.com).

```bash
git clone https://github.com/belkovskyy/text2sql-guardrails.git
cd text2sql-guardrails

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[app,dev]"

cp .env.example .env             # прописать доступ к своей БД
ollama pull qwen2.5:3b

python -m pytest                 # тесты защиты, БД не нужна
```

Поднять Northwind и веб-интерфейс:

```bash
docker compose up -d             # postgres + northwind.sql + роль text2sql_ro
python -m streamlit run apps/streamlit_app.py
```

Контейнер сразу создаёт роль `text2sql_ro` (только чтение), под которой и работает
приложение по умолчанию. В интерфейсе четыре вкладки: NL→SQL, выполнение SQL, поиск
по схеме, генерация документации по базе.

Все переменные окружения — в `.env.example`.

## Структура

```
text2sql/
  agent.py         пайплайн: промпт, вызов Ollama, извлечение SQL, self-healing
  guardrails.py    разбор SQL по токенам, блокировка небезопасного, LIMIT
  introspect.py    схема из Postgres (таблицы, колонки, внешние ключи)
  schema_search.py подбор релевантных таблиц под вопрос
  docgen.py        генерация Markdown-документации по базе
  db.py            выполнение SELECT, выдача в DataFrame
  config.py        загрузка .env
apps/streamlit_app.py   веб-интерфейс
docker/init/northwind.sql   схема и данные демо-базы
eval/                  примеры вопросов на русском
tests/                 тесты защиты и извлечения SQL
```

## Область применения

Проект про безопасность обращения LLM к базе, а не про точность генерации SQL — качество
самих запросов зависит от выбранной модели Ollama. Список опасных функций рассчитан
на PostgreSQL, фиксы синонимов — на схему Northwind; интроспекция и разбор запросов
от конкретной базы не зависят.
